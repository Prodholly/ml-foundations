## What I built

Day 1 was about getting data into a model. Day 2 is about what the model does with it.

A classifier's forward pass is mostly three operations: multiply the inputs by a weight matrix to get
scores (logits), turn those scores into probabilities with softmax, and measure how wrong those
probabilities are with cross-entropy. I built all three from scratch:

- `ops.py`: matrix multiply as three nested Python loops
- `einsum_matmul.py`: the same matrix multiply in one `np.einsum` line
- `softmax.py` and `einsum_softmax.py`: softmax, first on a single column of scores and then row by row
- `cross_entropy.py`: cross-entropy loss against one-hot targets
- `benchmark.py`: the loop, einsum and NumPy timed against each other on 500x500 matrices

## Design decisions

**Why write matmul as three loops first?**
`np.matmul` or `@` hides the whole operation. Writing it as loops forces every part to be explicit:
the outer two loops pick which output cell `C[i, j]` we are filling, and the inner loop walks along the
shared dimension `k`, multiplying and adding. Once you have written it this way, the shape rule
`(m, n) @ (n, p) -> (m, p)` stops being something to memorize. The outer loops run over `m` and `p`, so
those are the output's shape, and `n` is consumed by the inner loop, so it has to match on both sides.

It also gives the benchmark something honest to compare against. This loop is exactly what NumPy does
mathematically, so any speed difference comes from how it is executed, not what is computed.

**Why rewrite matmul with einsum?**
Einsum describes an operation by labelling the axes instead of writing loops. `'ik,kj->ij'` says the
first input has axes `i, k`, the second has `k, j`, and the output keeps `i, j`. The rules are:

1. Each letter is a loop variable.
2. A letter shared between inputs means those axes line up (here, the columns of `X` with the rows of `Y`).
3. A letter that is in the inputs but missing from the output gets summed over.

So `'ik,kj->ij'` maps directly onto the three loops: `i` and `j` are the outer loops, and `k` is the
inner loop that gets summed away. The nine lines of loop code collapse into one string, and the string
still shows which axis is being contracted, which `X @ Y` does not.

The same notation covers operations that otherwise each have their own function:

| einsum | equivalent | operation |
|---|---|---|
| `'ij->ji'` | `X.T` | transpose |
| `'i,i->'` | `np.dot(a, b)` | dot product |
| `'ii->'` | `np.trace(X)` | trace |
| `'bik,bkj->bij'` | `X @ Y` on stacks | batched matmul |

The last one is the reason einsum is worth learning now. Attention in a transformer is a batched matmul
over (batch, heads, sequence, dimension) axes, and einsum is the clearest way to write it without
losing track of which axis is which.

**Why use einsum in softmax, and is it actually simpler there?**
In `softmax_einsum`, `'ij,i->ij'` multiplies every element `[i, j]` of the exponentiated matrix by
`1 / row_sums[i]`. No letter disappears after the arrow, so nothing is summed. It is a per-row scale.

To be honest, this is not simpler than plain broadcasting. `exp_z / exp_z.sum(axis=1, keepdims=True)`
does the same thing and is what most code uses. I used einsum here to practise reading the notation on
a case where nothing is summed, which shows that einsum is about labelling axes, not only about
contracting them.

**Why subtract the max before `exp` in softmax?**
`np.exp(1000)` overflows to `inf`, and `inf / inf` is `nan`. Softmax gives the same output if you shift
every input by the same constant, because the shift cancels between the top and bottom of the fraction:

```
exp(z_j - c) / sum_k exp(z_k - c) = exp(z_j) / sum_k exp(z_k)
```

Choosing `c = max(z)` makes the largest exponent `exp(0) = 1` and every other one smaller, so nothing
can overflow. It costs one extra subtraction and changes nothing mathematically.

**Why move from a `(1, 4)` weight vector to a `(3, 4)` weight matrix?**
In `softmax.py` the weights were a single vector, so `z = X @ w.T` had shape `(3, 1)`: one score per
sample. Running softmax over that column gives probabilities *across samples*, which answers "which of
these three samples is most likely?". That is not a classification question.

For classification each sample needs one score per class, so in `einsum_softmax.py` I gave each of the 3
classes its own weight vector, `w` with shape `(3, 4)`. Now `z` is `(3, 3)`, one row per sample and one
column per class, and softmax runs along each row. That is the multiclass setup the rest of the
curriculum will use.

**Why store weights as `(classes, features)` and transpose with `w.T`?**
Each row of `w` is one class's weight vector, which is easy to read and inspect. The matmul needs the
features on the inner dimension, so `X (3, 4) @ w.T (4, 3)` lines up the 4 features and leaves
`(samples, classes)`. PyTorch's `nn.Linear` uses the same convention: its weight has shape
`(out_features, in_features)` and the forward pass computes `x @ W.T`.

**Why `1e-9` inside the log in cross-entropy?**
If the model gives the correct class a probability of exactly 0, `log(0)` is `-inf` and the loss
becomes infinite. Adding a tiny constant caps the worst case at `-log(1e-9) ≈ 20.7` instead. It is a
patch rather than a real fix; see "What PyTorch does differently".

**Why `np.mean` over the batch instead of `np.sum`?**
With a sum, the loss doubles when the batch size doubles, so the gradient's size, and therefore a good
learning rate, would depend on batch size. Averaging keeps the loss on the same scale whatever the batch
size is.

**Why one-hot targets?**
With one-hot `y_true`, `y_true * log(y_pred)` is zero for every class except the correct one, so the
sum over classes picks out exactly `log(probability of the correct class)`. The whole loss reduces to
"how much probability did you give the right answer?", which makes it easy to reason about.

## The benchmark

### Results (500x500 matrices, MacBook Air)

```
Loop matmul:   39.9447 seconds
NumPy matmul:  0.0027 seconds
einsum matmul: 0.0204 seconds

NumPy is 14659x faster than my matmul loop
NumPy is 7.5x faster than einsum
```

### Why 500x500?

The loop does `n³` multiply-adds, so 500x500 is 125 million of them. That size was chosen to sit
between two failure modes:

- **Too small** (say 3x3, 27 multiply-adds): all three methods finish in microseconds, and the time is
  dominated by function-call overhead and timer noise rather than the multiplication itself. The
  comparison would mean nothing.
- **Too big** (say 2000x2000): `n³` grows fast. 2000 is 4x bigger than 500, so the loop would take
  4³ = 64x longer, around 40 minutes. NumPy would still finish in well under a second.

500 is large enough that the arithmetic dominates and small enough that the loop finishes in under a minute.

### Checking the `n³` claim

The demo runs the same loop at 200x200 and took about 2.67 s on the same machine. If time scales with
`n³`, going from 200 to 500 should cost `(500/200)³ ≈ 15.6x` more. The measured ratio is
`39.9 / 2.67 ≈ 15x`. The loop really is cubic, and each multiply-add costs about 0.32 µs in both runs
(`39.9 s / 125M` and `2.67 s / 8M`).

### Why is NumPy ~15,000x faster?

The arithmetic is identical, so the gap is all execution:

- **Interpreter overhead.** Each pass of the inner loop runs the Python interpreter: look up `X[i, k]`,
  wrap the result in a Python float object, multiply, look up `C[i, j]`, add, store it back. That is
  around 0.3 µs of bookkeeping for one multiply-add a CPU can do in under a nanosecond.
- **Compiled BLAS.** `np.matmul` hands the work to a BLAS library (on this Mac, Apple Accelerate). BLAS
  is compiled machine code that uses SIMD instructions to do several multiply-adds per CPU instruction,
  arranges the work in blocks that fit in the CPU cache, and can use multiple cores.

### Why is einsum in the middle?

Einsum is also compiled C, so it avoids the interpreter overhead and is about 2,000x faster than the
loop. But by default (`optimize=False`) it runs its own general-purpose loop that works for any
subscript string, rather than calling the specialised BLAS routine. That generality costs the 7.5x.

Passing `optimize=True` lets einsum recognise that `'ik,kj->ij'` is a plain matmul and send it to BLAS.
Measured with `timeit` on 500x500: `np.matmul` 0.75 ms, `einsum` 18.4 ms, `einsum(optimize=True)`
0.75 ms. So the 7.5x is not the price of einsum notation, only of its default setting.

### Caveats on the timing method

`benchmark.py` times one run of each method with `time.time()`. That is fine for a 15,000x gap but too
rough for small differences:

- A single run includes one-off warm-up costs. The NumPy matmul took 2.7 ms in the benchmark but 0.75 ms
  as the best of repeated `timeit` runs.
- `time.time()` is wall-clock time and can jump if the system clock changes. `time.perf_counter()` is
  the right clock for measuring durations, so the demo uses that.

For anything closer than 2x, use `timeit` with several repeats and report the minimum.

## Known issues

These turned up while reviewing the code and tests. They are written down rather than silently patched,
so the next session starts from an honest list.

**`softmax_einsum` uses the max of the whole matrix, not each row.**
`np.max(z)` should be `np.max(z, axis=1, keepdims=True)`. With the global max, a row whose values are
all far below the global max underflows to all zeros, and `0 / 0` gives `nan`:

```python
softmax_einsum(np.array([[1000., 0.], [0., -1000.]]))
# [[ 1.  0.]
#  [nan nan]]
```

The current tests use `np.random.rand`, whose values are all between 0 and 1, so they never trigger it.

**`softmax` in `softmax.py` normalizes over the whole array.**
`np.sum(exp_z)` with no axis sums all elements. That is correct for the original `(3, 1)` column but
wrong for a `(3, 3)` logits matrix: the 9 probabilities sum to 1 together, instead of each row summing to
1. The standalone run of `cross_entropy.py` uses this function, which is why it reports a loss above 2 (2.07 to 2.38
across runs) while the demo, which uses the row-wise `softmax_einsum`, reports about 1.16.

**`matmul` does not validate shapes.**
It takes the inner dimension from `Y.shape[0]` and never checks it against `X.shape[1]`. With
`X (3, 4)` and `Y (2, 3)` it silently uses only the first 2 columns of `X` and returns a wrong `(3, 3)`
result. Day 1's DataLoader raised a `ValueError` on bad input, and this should too.

**The tests are not seeded.**
The `np.random.rand` inputs change every run, so a failure could not be reproduced. They should use
`np.random.default_rng(seed)`.

## Key concepts encountered

**A sanity check for cross-entropy at initialization**
With 3 classes, a model that knows nothing and guesses `1/3` for every class has loss
`-log(1/3) = ln(3) ≈ 1.0986`. The demo's random weights give 1.1583, close to that baseline, which is
what an untrained model should look like. If a fresh model's loss is far above `ln(num_classes)`, it is
confidently wrong before training starts, and something in the setup is off. For comparison, a model
that is 90% confident and always right gets 0.1054.

**`if __name__ == "__main__":`**
Python runs a whole file when you import it. Each file in `linalg/` mixed its function with demo code
that made random matrices and printed them, so importing `matmul` in a test also ran the demo. The guard
keeps the demo for `python -m linalg.ops` while making imports side-effect free.

**pytest's `pythonpath` and `testpaths`**
The tests originally passed only when run from inside `2_linalg/`. Adding `pythonpath` and `testpaths`
under `[tool.pytest.ini_options]` in the root `pyproject.toml` lets `pytest` find and import everything
from any folder in the repo.

## What NumPy and PyTorch do differently

**Matmul dispatches to vendor libraries**
`torch.matmul` on CPU calls a BLAS library just as NumPy does, and on GPU it calls cuBLAS. Neither ever
runs a Python-level loop. The loop here exists to show the computation, never to be used.

**Cross-entropy takes logits, not probabilities**
`torch.nn.functional.cross_entropy` takes raw logits and computes `log_softmax` internally using the
log-sum-exp trick, `log_softmax(z) = z - max(z) - log(sum(exp(z - max(z))))`. It never forms a
probability and then takes its log, so it never needs the `1e-9` patch. It is more accurate when
probabilities are tiny, and it is one fused operation instead of two.

**`torch.einsum` plans the contraction order**
For einsum calls with three or more inputs, the order you contract them in can change the cost by orders
of magnitude. PyTorch (and NumPy with `optimize=True`) searches for a cheap order before computing.
With only two inputs, as here, there is just one order, and the only question is whether BLAS gets used.
