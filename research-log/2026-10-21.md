## Design decisions

**Why `Generic[T]` instead of hardcoding `np.ndarray`?**
The DataLoader should work on any sequence type, not just numpy arrays. Using
`TypeVar` and `Generic[T]` makes the class reusable across strings, integers,
custom sample objects, or anything else a user wraps in a list. The type system
then catches mismatches at the editor level before runtime.

**Why `random.Random(seed)` instead of `random.seed(seed)`?**
`random.seed()` sets global state and bleeds into any other code in the same
process that uses the `random` module. `random.Random(seed)` creates an isolated
RNG instance scoped to this DataLoader object. Two loaders with different seeds
never interfere with each other.

**Why `yield` instead of returning a list of batches?**
A generator pauses after each batch and resumes on demand; this is what we want. The alternative which is
building all batches upfront, would load the entire dataset into memory at once.
For a 500GB image dataset with batch size 32, that difference is the difference
between training and crashing your RAM because you are loading the entire dataset before you start training.

**Why shuffle indices instead of shuffling the dataset?**
Shuffling the dataset directly would rearrange the user's original data permanently,
which is unexpected and hard to undo. Instead, we shuffle a list of integers (the indices of the data; not the data itself) and use those as pointers into the dataset. The original data never moves.

## Key concepts encountered

**Dunder methods as a protocol**
Python's `for x in obj` syntax calls `obj.__iter__()`. The DataLoader does not
inherit from any base class to support iteration. It simply implements the two
methods Python looks for: `__len__` and `__iter__`. This is duck typing and it
is how most of Python's standard library works.

**Callable as a type**
`Callable[[list[T]], np.ndarray]` is a type description.
It says that any function that accepts a list of T and returns an ndarray qualifies.
This is how you write flexible APIs that accept user-defined behavior without
requiring inheritance or registration.

**Editable installs**
`pip install -e .` registers the package with the Python interpreter by pointing
at the source directory directly. Edits to `core.py` take effect immediately
without reinstalling. This is the standard workflow for developing a library
alongside code that uses it.

## What PyTorch does differently

**Parallel worker processes**
While the GPU is training on batch 1, PyTorch is already loading batch 2 from disk
in the background using separate CPU processes. Loading and training happen at the
same time, so the GPU is never sitting idle. 

However, my own implementation basically loads batch 1, hands it to the GPU for training, waits for training to finish, then loads batch 2. There is a pause between
each batch where the GPU is doing nothing and just waiting for data. For small
datasets this pause is barely noticeable. For large datasets with millions of images
stored on disk, this pause compounds across thousands of batches and significantly
slows down the total training time. Parallel workers eliminate that pause entirely.

**Sampler abstraction**
In my implementation, `__iter__` does two things: decides which indices to use,
and assembles the batches from those indices. PyTorch splits these into two separate
objects. The `Sampler` is only responsible for producing indices. The `DataLoader` is
only responsible for turning those indices into batches. This separation means you
can swap in a custom `Sampler` for weighted sampling (where some samples appear more
often than others during training) without touching the batching logic at all.

**Pin memory**
When data moves from RAM to the GPU, it normally goes through an extra copy step
in the CPU. Pin memory reserves a special region of RAM that the GPU can read
directly which makes it skip that intermediate copy and making the transfer faster. This is a
low-level hardware optimization that matters at scale.

My own implementation, however, handles none of that, which is the point. All three features
are layers built on top of the same core idea I built: take a dataset,
produce batches. By building the simple version first, one can see the skeleton
clearly. And when we read PyTorch's source code, you will recognize the core and
understand exactly what each added layer is doing and why it exists.
