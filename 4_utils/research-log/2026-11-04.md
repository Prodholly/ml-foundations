## What I built

Days 1 to 3 each built one bigger thing. Day 4 is about the small functions that hold ML code together,
and about writing them the way production code is written.

Three typed utility functions, all in `utils/ml_utils.py`:

- `batch_items(items, batch_size)`: splits a flat list into batches, with a smaller last batch if needed
- `check_shape(tensor, expected_shape)`: confirms a NumPy array has the expected shape, or raises an error
  showing actual vs expected
- `safe_parse_int(value, default=None)`: converts any value to an int, returning `default` instead of crashing

Each function has an explicit input/output contract, handles its edge cases, has a time and space
complexity analysis, and is covered by tests. The tests got the most attention today, because I found
that a passing test doesn't always prove what I thought it did.

## Design decisions

### Contracts in general

**Why spell out a contract for such small functions?**
A contract says what goes in, what comes out, and what happens at the edges. Writing it down first forces
the awkward questions early: what does an empty list return? What counts as a bad batch size? The edge
cases in the spec turned straight into tests, so the contract and the tests describe the same thing.

**Why type hints and runtime checks?**
Python doesn't enforce type hints. `check_shape(None, (3, 4))` runs whatever the signature says. The hints
are for readers and editors, and they document the contract right where the function is defined. The
runtime checks are what actually stop bad input.

**Why `TypeError` for some problems and `ValueError` for others?**
They answer different questions. `TypeError` means "this isn't the kind of thing I accept": `None`, or a
plain list where an array should be. `ValueError` means "the kind of thing is right, but the value isn't":
an array with the wrong shape, or a `batch_size` of 0. Using the right one lets the caller handle each case
on purpose.

**Why `raise` and never `assert`?**
`assert tensor.shape == expected` looks like the same check, but Python removes every `assert` when run with
the `-O` flag. A check that can be switched off by a command-line flag isn't a contract. `raise` always runs.

### `batch_items`

**Why check `batch_size` before checking for an empty list?**
The order changes one case: `batch_items([], 0)`. Checking the list first would return `[]` and hide the
bad argument. A `batch_size` of 0 is a bug in the caller whatever the data looks like, so it should fail
every time, not only when there happens to be data.

**Why keep the empty-list check when the loop already handles it?**
`range(0, 0, batch_size)` produces nothing, so the loop returns `[]` on its own. I confirmed this when a
test run showed that removing the check changes nothing. I kept it anyway, because the contract lists
"empty list returns `[]`" as its own case, and the check makes that case visible in the code.

**Why return a list of batches and not a generator?**
The contract returns `list[list[Any]]`, which is right for lists that fit in memory, and it lets the
caller use `len()` or index into the result. Day 1's DataLoader made the opposite choice and used a
generator, because it has to handle datasets too large to hold twice. The two are the same idea at
different scales.

**Why keep a smaller last batch?**
`[1, 2, 3, 4, 5]` in batches of 2 gives `[[1, 2], [3, 4], [5]]`. Every item comes out once, and nothing is
silently dropped. Throwing away a partial batch is a training decision, which is why Day 1 made it an
option (`drop_last`) rather than the default.

**Why slicing?**
`items[start : start + batch_size]` gives each batch as a new list in one step, and a slice past the end of
the list just stops at the end, so the last batch needs no special case.

### `check_shape`

**Why return `True` or raise, and never return `False`?**
A function that returns `False` relies on every caller remembering to check it, and forgetting is silent.
Raising stops the program at the exact line where the shape went wrong, before a badly shaped array reaches
a model and causes a confusing error ten steps later. Returning `True` on success still means it can be used
in a condition.

**Why put both shapes in the error message?**
`Shape mismatch: expected (4, 3), but got (3, 4)` contains the diagnosis: the same numbers reversed means
the array is transposed. A message that only said "wrong shape" would send me looking for the problem.

**Why an `isinstance` check as well as the `None` check?**
The contract says the input is a NumPy array, but only `None` was handled. A plain list got as far as
`.shape` and crashed with `AttributeError: 'list' object has no attribute 'shape'`, which describes the
symptom rather than the mistake. The `isinstance` check turns it into `TypeError: tensor must be a NumPy
array, got list`. I kept the separate `None` check because "cannot be None" is a clearer message for the
most common mistake.

### `safe_parse_int`

**Why return a default instead of raising?**
This function is for messy data, like a column read from a file where some cells say `"N/A"`. Raising on the
first bad value would stop the whole job for one cell. Returning a default lets the caller decide what a bad
value becomes.

**Why does the default default to `None`?**
`None` means "this couldn't be parsed", and it can't be confused with a real value. A default of `0` would
make `"abc"` indistinguishable from `"0"`. A caller who wants a number can pass `default=-1` or `default=0`.

**Why truncate floats?**
That's what the contract asks for, and it's what `int()` does: it drops everything after the decimal point.
That means it rounds toward zero, so `3.9` becomes `3` and `-3.9` becomes `-3`. Rounding down with
`math.floor` would give `-4`, so I added a negative case to the tests to pin the behaviour down.

**Why catch exactly `ValueError`, `TypeError` and `OverflowError`?**
Each one is a real way a value can fail to become an int: `int("abc")` raises `ValueError`, `int([1])` raises
`TypeError`, and `int(float("inf"))` raises `OverflowError`. A bare `except:` would also catch things that
aren't about the value at all, like Ctrl+C, and could hide genuine bugs.

### Tests

**Why `parametrize`?**
Several cases share one check: `batch_size` of 0 and -1, three wrong shapes, and positive and negative
floats. `@pytest.mark.parametrize` runs the same test once per input and reports each one separately.

**Why `match=` on `pytest.raises`?**
`pytest.raises(ValueError)` only checks the type of the error, not where it came from. Adding `match=` checks
the message, which proves the error came from my own check. Two of my tests needed this, as explained under
"Challenges and fixes".

## Complexity analysis

| Function | Time | Space | Notes |
|---|---|---|---|
| `batch_items` | O(n) | O(n) | n = number of items |
| `check_shape` | O(1) | O(1) | shape is stored metadata |
| `safe_parse_int` | O(1) | O(1) | single value conversion |

**`batch_items`: O(n) time, O(n) space**
The loop runs about `n / batch_size` times, and each slice copies `batch_size` items, so every item is copied
exactly once: O(n) time. The batches together hold all n items, so that's O(n) extra space too. The copy is
shallow, though. The outer lists are new, but the items themselves aren't duplicated. A list of a million
images would get new lists of references, not a million new images.

**`check_shape`: O(1)**
A NumPy array stores its shape as a small tuple next to the data. Checking it never touches the data, so a
`(3, 4)` array and a `(10_000, 10_000)` array take the same time. Strictly, comparing two shape tuples is
O(d), where d is the number of dimensions, but d is 2 to 5 for nearly every ML array, so it's constant in
practice.

**`safe_parse_int`: O(1)**
One value, one conversion. Strictly, converting a string costs time proportional to its number of digits,
but real values have a handful of digits. Python also caps the work: since Python 3.11, converting a string
of more than 4,300 digits raises a `ValueError`, which `safe_parse_int` turns into the default. That limit
exists so very long strings can't be used to make a program slow.

**Why put the table at the top of `ml_utils.py`?**
The cost of a function is part of its contract. With the table in the file, anyone choosing whether to call
`batch_items` on a huge list sees the cost before they read the code.

## Challenges and fixes

**A test that silently disappeared.**
I had two functions called `test_check_shape_wrong`. Python lets a name be defined twice, and the second
definition replaces the first, so pytest only ever saw one. Nothing warned me. The first one also built an
array and asserted nothing, so it wouldn't have tested anything even if it had run. I renamed the tests so
each has its own name.

**A missing test from the spec.**
The spec asked for "None raises TypeError", and there was no such test. I added `test_check_shape_none`.

**`safe_parse_int` could still crash.**
The contract promises a default instead of a crash, but `safe_parse_int(float("inf"))` raised
`OverflowError: cannot convert float infinity to integer`. I was only catching `ValueError` and `TypeError`.
Adding `OverflowError` fixed it, and `float("nan")` was already safe because it raises `ValueError`. Both now
have a test.

**A confusing error from the wrong kind of input.**
Passing a plain list to `check_shape` gave `AttributeError: 'list' object has no attribute 'shape'`. I added
an `isinstance` check so it raises a `TypeError` that names the problem.

**Tests that passed for the wrong reason.**
To check that my tests actually catch bugs, I put bugs into a copy of `ml_utils.py` one at a time and ran the
tests against each. Two bugs got through:

- Changing `batch_size <= 0` to `batch_size < 0` should let 0 through, but the 0 test still passed. Python's
  `range()` raises its own `ValueError` when the step is 0, so the test got the error type it expected from
  the wrong place.
- Removing the `None` check should break the `None` test, but it still passed, because the new `isinstance`
  check also rejects `None` with a `TypeError`.

In both cases the test only checked the type of error. Adding `match=` to check the message fixed both, and
now each bug fails at least one test.

**Two pytest configurations.**
I added a `pyproject.toml` inside `4_utils` so that `pytest tests/` would work from inside the folder. The root
`pyproject.toml` already handles that for every day, and the extra file took over whenever pytest ran Day 4's
tests: it reported `rootdir: 4_utils` instead of the repo root, even when started from the root. I removed it
so every day uses one configuration.

## Key concepts encountered

**Big-O is about growth, not speed**
O(n) doesn't say how fast `batch_items` is. It says that doubling the list roughly doubles the work. O(1)
says the work doesn't grow with the input at all. Reading "O(1)" honestly also means saying what the constant
depends on: the number of dimensions for `check_shape`, and the number of digits for `safe_parse_int`.

**What `int()` really accepts**
`int()` does more than it seems. It truncates floats, strips surrounding whitespace (`" 42 "` becomes 42),
allows underscores as digit separators (`"4_2"` becomes 42), turns `True` into 1, and reads bytes (`b"7"`
becomes 7). It won't parse a decimal string, so `int("3.9")` raises. Knowing all this matters, because
`safe_parse_int` inherits every one of these behaviours.

**Redefining a name replaces it**
`def` is just an assignment to a name. Defining a test function twice is like writing `x = 1` then `x = 2`, so
the first one is gone. pytest can only run what still exists at the end of the file.

**A passing test isn't proof**
A test proves something only if it would fail when the code is wrong. Deliberately breaking the code and
checking that a test fails is the most direct way to know, and it found two weak tests today that looked fine.

## What Python, NumPy and PyTorch do differently

**`itertools.batched` (Python 3.12+)**
The standard library now has `itertools.batched(items, n)`, which does the same split. It returns batches
lazily, one at a time, like Day 1's generator, and gives tuples rather than lists. For large inputs it's the
better choice, and it's worth knowing before writing your own.

**NumPy and PyTorch splitting**
`torch.split(tensor, size)` works like `batch_items`, with chunks of a given size and a smaller last one.
`np.array_split(array, k)` is different: its second argument is the number of pieces, not the size of each, so
`np.array_split(range(10), 4)` gives 4 pieces of sizes 3, 3, 2 and 2.

**Shape checks in PyTorch**
PyTorch checks shapes inside its own operations, so a mismatched matmul raises an error saying which sizes
don't line up. Checking at the boundary of your own code, as `check_shape` does, catches the mistake earlier,
where the error message can still say which array is wrong.

**Parsing a whole column at once**
For a full column of data, `pd.to_numeric(values, errors="coerce")` from Day 3 is the fast, vectorized version
of `safe_parse_int`: it turns everything that can't be parsed into a missing value in one call.

## Known limitations

- `safe_parse_int("3.9")` returns the default, because only real floats are truncated.
- `" 42 "`, `"4_2"`, `True` and `b"7"` all parse as integers, which may be more forgiving than wanted.
- Strings longer than 4,300 digits return the default.
- `check_shape` needs a tuple. A list like `[3, 4]` fails with a message that looks like a match.
- `check_shape` has no wildcard for "any size" in one dimension.
- `batch_items` builds every batch up front, so memory use doubles for the length of the call.
- `utils` is a common package name, so it could clash with another installed package of the same name.

## Open questions

Each of these changes one of today's contracts. If you try one, write the new edge case as a test first and
watch it fail, the same way I checked the tests above.

- How would you add a wildcard to `check_shape`, so `(None, 3)` means "any batch size, but 3 features"?
- Should `safe_parse_int("3.9")` return 3? What would you have to change, and what new edge cases would that
  bring in, like `"1e3"`?
- Should `safe_parse_int(True)` return 1, or treat a boolean as a bad value? Where could accepting it cause a
  quiet bug?
- How would you rewrite `batch_items` as a generator, and what would change in its contract and its tests?
