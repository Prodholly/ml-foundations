# Day 3: Scientific Data Explorer

**Date:** 2026-10-31

**Status:** Complete, with known limitations listed below

## What I built

Day 1 got data into a model and Day 2 covered what the model does with it. Day 3 steps back to the question
that comes before both: what is actually in this dataset?

This is a command-line tool that takes any CSV or TSV file and prints one table row per column:

- **dtype:** what kind of data the column holds (number, text, date, or empty)
- **null %:** what percentage of its values are missing
- **unique count:** how many distinct values it has
- **mean, std, min, max:** summary statistics, for numeric columns only

My other goal today was to practise decomposing a project. Before any code, I wrote each file out as numbered
pseudocode, so the structure was decided before the details. The build order then came from the dependencies:
the profiler first because it depends on nothing else in the project, then its tests, then the CLI around it.

## Design decisions

### How the tool is structured

**Why split the code into `profiler.py` and `data_explorer.py`?**
`profile()` only calculates. It takes a DataFrame and returns data, with no files, arguments or printing.
`data_explorer.py` deals with everything around that. The split is what makes the profiler easy to test: a
test can build a 5-row DataFrame by hand and check the answer, without creating files or reading terminal
output. It also tells me where a bug must be. A wrong number comes from the profiler, and a crash on a bad file
comes from the CLI.

**Why does `profile()` return a list of dicts?**
One dict per column is one row of the output table, so the data already has the shape of the result. Each key
names its own value, so `row["null_pct"]` reads more clearly than a position in a tuple. The result flips the
data's layout: each column of the dataset becomes one row of the profile, so 50 rows by 12 columns of data
becomes 12 rows by 8 columns of profile.

**Why use `None` for missing stats and only format at the end?**
The spec says non-numeric columns get `None` from the profiler and "—" in the table. Keeping those separate
means the profiler returns real values at full precision and only the copy going to the screen becomes text.
`rich` needs strings for its cells anyway, and a plain float can't remember "always show 2 decimals".

**Why a positional `filepath` instead of `--dataset`?**
My first draft used `--dataset`, but the file is the one thing the tool cannot run without. In argparse, a name
without dashes is required and a name with dashes is optional, so a positional argument matches what it means.
It also makes the command shorter. `--sep` is optional with a default of `,`, so CSV files need no extra typing.

### How a column gets its type

**Why my own labels instead of pandas' dtypes?**
Printing `float64` or `str` describes how pandas stores a column, not what the column means. An integer column
with blanks loads as `float64`, and a date column loads as `str`. Labels of `number`, `text`, `date` and `empty`
answer the question someone actually has when reading the table.

**Why does the "empty" check come first?**
An all-blank column has nothing to tell pandas its type, so it loads as `float64`. That means
`is_numeric_dtype` says yes, and `.mean()` returns `nan` rather than `None`. Checking for "no real values" before
checking for "numeric" gives that column an honest label and no misleading stats. The order of the checks is the
logic here: empty, then number, then date, and text is whatever is left.

**Why detect dates with `errors="coerce"` and a fixed format?**
pandas loads dates as plain text unless you tell it otherwise, so the profiler has to test for them.
`errors="coerce"` turns anything that isn't a date into a missing value, so "nothing went missing" means every
value was a date. Fixing the format to `%Y-%m-%d` stops pandas warning about guessing a format on every text
column. The trade-off is that other date formats are labelled `text`, which is listed under known limitations.

**Why run `dropna()` before the date check?**
A blank stays missing after conversion, so it looks exactly like a failed date. `col_6` has 48 dates and 2 blanks,
and with the blanks left in, asking "did everything convert?" would get a no and label it text. Dropping them
first means any failure is a real failure. The stats don't need this because pandas already skips missing values.

**Why convert the stats with `float()`?**
pandas returns NumPy number types. They do arithmetic the same way, but they print as `np.float64(25.5)` inside a
dict, and `np.int64` would break `json.dumps` if I ever save a profile. Converting means anything calling
`profile()` gets plain Python values. It also makes `min` and `max` floats on integer columns, so they all
display with 2 decimals.

**Why the sample standard deviation?**
pandas' `.std()` divides by `n - 1` and NumPy's `np.std()` divides by `n` by default. A dataset is usually a
sample of something larger, so I kept the pandas default. It's a choice worth writing down, because the two give
different answers: `col_1` is 14.5774 with pandas and 14.4309 with NumPy.

### How the CLI loads and displays data

**Why try UTF-8 and then latin-1?**
UTF-8 is the modern default, and it rejects bytes that aren't valid, so it fails loudly on older files. latin-1
can decode any byte, which makes it a safe fallback. That same fact means the "both encodings failed" branch
should almost never run. I kept it because it was in the plan, but I couldn't trigger it, and it's the one branch
that is untested.

**Why print errors to stderr and exit with code 1?**
A person running the tool should see one clear line and not a Python traceback. Normal output and errors go to
separate channels, so `python data_explorer.py nope.csv > results.txt` still shows the error on screen and leaves
it out of the file. The exit code tells other programs that the run failed.

**Why test `is None` and not `if not value`?**
`col_9` is constant, so its std is exactly `0.0`, and `0.0` is falsy. `if not value` would show "—", which reads
as "no result" when the real result is zero. The table has to tell "the answer is 0" apart from "there is no answer".

**Why turn off rich's markup and emoji codes?**
`rich` reads text like `[red]` as formatting and `:smile:` as an emoji. That's useful for text I write, but column
names come from someone else's file. The rule I took from this: text from a user's file is data, never
instructions. Styling can still be added through `style=` settings, which live in the code.

### How the tests and sample data are set up

**Why three versions of the sample data?**
The data should be built around the task, and it took me a few tries to see that:

1. All integers. Clean, but there was nothing for a profiler to find.
2. Integers with some strings mixed in. Closer, but `unknown` turned columns into text and nothing tested dates.
3. One column per case, working backwards from the four profile fields. This is the version I kept.

**Why exact null counts instead of random ones?**
In version 2, each cell had a 20% chance of being replaced, so one column landed on 36%. For a test fixture, I
want to know the right answer in advance, so version 3 blanks out exactly `n` randomly chosen cells. The random
generator is seeded, so `generate_data.py` always produces identical files.

**Why build test data by hand instead of reading `data.csv`?**
With 5 rows I can work out the right answer myself, and changing the sample files can't break the tests.

**Why compare against `df.columns` and look rows up by name?**
Comparing with `len(df.columns)` rather than a hard-coded 3 means adding a column can't break the test. Most tests
use `by_column["score"]` so they don't depend on the order of the results. The one exception is
`test_returns_one_row_per_column`, which uses the raw list on purpose. A dict can't hold a key twice, so a bug that
added a column twice would be hidden by `by_column`.

**Why list dependencies in `pyproject.toml`?**
pandas and rich go in `dependencies` so that one `pip install -e ".[dev]"` sets up the whole repo. pytest goes in
an optional `dev` group, which separates what the code needs to run from what I need while developing it.

## Challenges and fixes

These are the things that went wrong along the way, because the mistakes taught me more than the parts that
worked first time.

### Building the profiler

**Paths that weren't paths.**
My first attempt was `Path(/data.csv)`. Without quotes it's a `SyntaxError`, and the leading `/` would have meant
the very top of the disk, not the project. The fix was `Path(__file__).parent.parent / "data"`, which builds the path
from where the script lives, so it works from any folder.

**Two names for one variable.**
Both paths were assigned to `data_one`, so the second overwrote the first. Each one needed its own name.

**Four bugs in the first version of `profile()`.**

| Bug | What happened | Fix |
|---|---|---|
| `len(df.shape[1])` | `TypeError`, because `shape[1]` is already a number | loop over `df.columns`, which also gives the name for the dict |
| `len(column) / nulls` | Upside down: 500% instead of 20%, and `inf` with no nulls | missing values divided by total rows |
| `.unique()` | Returns the values themselves, including missing ones | `.nunique()` returns a count without them |
| Empty `else:` | `SyntaxError`, so the file wouldn't run | fill in the date and text checks |

**Reading a file on import.**
I had `df = pd.read_csv(...)` at the top of `profiler.py`, which ran on every import. This is the same mistake I
fixed on Day 2. `profile(df)` receives its data as an argument, so loading moved into `data_explorer.py`.

**`nan` in an empty column.**
`col_12` passed the numeric check and returned `nan` for its stats, which would have printed `nan` rather than "—".
Checking for an empty column first fixed it.

**Understanding mixed columns.**
I expected a column like `10, 20, abc, 40` to keep its numbers as numbers. It doesn't. A CSV holds only text, and
pandas converts a whole column or none of it, so one stray `abc` leaves all of it as text. The profiler reports that
as `text` with no stats. It's correct given what pandas loaded, but it can hide a mostly numeric column, so it's
listed under known limitations.

### Building the CLI

**`argparse` mix-ups.**
My first draft called `argparse.ArgumentError()`, which is an exception, instead of `ArgumentParser()`. It also
passed `description=` to `add_argument`, when that belongs on the parser.

**`--sep "\t"` isn't a tab.**
`\t` only means tab inside Python source code. In the terminal it arrives as two characters, a backslash and a `t`.
`load_file` now converts those two characters into a real tab before calling pandas.

**A bracket in a header crashed the table.**
A CSV with a column named `[/x]` raised `rich.errors.MarkupError`, because `rich` read it as a closing tag with no
opening tag. Valid data shouldn't be able to crash a data tool. `Console(markup=False, emoji=False)` fixed it.

**`nan` in the Std column.**
That same test file had one data row, and the table printed `nan` for std, because a sample std needs at least two
values. `format_value` now shows "—" for `nan` as well as `None`.

**Yellow underlines on working code.**
The yellow underline on `from rich.console import Console` wasn't a code problem. `rich` was listed in
`pyproject.toml` but hadn't been installed yet. Adding a dependency to the file and installing it are two steps.

**A script and a folder with the same name.**
`data_explorer.py` and `data_explorer/` share a name. The import works because Python picks the folder, but it means
nothing can import `print_table` from the script, which is why `examples/demo.py` prints plain values. A name like
`cli.py` would have avoided this, and I've kept that in mind for later builds.

### Building the tests

**Using a function without calling it.**
`make_sample_df["score"]` raised `TypeError: 'function' object is not subscriptable`, because it was missing the
`()`. Also, `profile` needs the whole DataFrame, so a single column gets picked out of the result, not the input.

**Changing the data changes the answers.**
I moved the sample data from 4 rows to 5, so 1 missing value became 20% instead of 25%, and the planned stats for the
later tests changed too. Expected values have to follow the fixture.

**`python3 tests/test_profiler.py` failed.**
This gave `ModuleNotFoundError: No module named 'data_explorer'`. A script looks for imports in its own folder,
which is `tests/`. Even with the import fixed, it would only define the functions and never run them.
`pytest` is the right command, and the `pythonpath` setting in `pyproject.toml` is what lets it find the package.

**A gap the plan missed.**
The sample dates had no blanks, so nothing tested the `dropna()` date behaviour. I added
`test_date_column_with_missing_values` for the `col_6` case.

**A wrong expected value.**
My first table of expected values listed the `col_7` max as 99245.20, but the true value is 99245.18. The cause was
printing with `:g`, which keeps 6 significant digits. The real run showed the difference, and the table above is
corrected. If you're using numbers as expected answers, print them at full precision.

## Key concepts encountered

**A CSV has no types**
Every value in a CSV is text, whether or not it has quotes. pandas tries to convert each column as a whole, so the
type you see after loading is a guess about the column, not a fact about the file.

**One column, one type**
A column has a single dtype, which is what makes calculations on it fast. This explains several surprises today:
integers with blanks become `float64` because `NaN` is a float, and one stray string makes the whole column text.

**stdout, stderr and exit codes**
A program has two output channels. `>` and `|` only carry stdout, so errors sent to stderr still reach the screen.
The exit code is the machine-readable version of the same signal: 0 for success, and non-zero for failure. argparse
exits with 2 when a required argument is missing.

**Unpacking with `*`**
`table.add_row(*values)` turns one list into separate arguments. Python can tell this from multiplication by where
the `*` sits: in front of a list in a function call, it unpacks.

**`if __name__ == "__main__":` as a habit**
This came back from Day 2 twice: once as the bug of reading a file on import, and again as how the CLI starts.

## What pandas and real profiling tools do differently

**pandas already covers parts of this**
`df.info()` shows dtypes and non-null counts, and `df.describe(include="all")` adds summary stats. What they don't do
is give one row per column with null percentages and meaningful type labels in a single view, which is the gap
this tool fills.

**`read_csv` has options I didn't use**
`na_values` adds custom missing-value markers such as `unknown`, `parse_dates` converts dates while loading, and
`on_bad_lines` decides what happens to rows with too many fields. Exposing these as CLI options would fix several
of the limitations below.

**Real profilers do much more**
Libraries like ydata-profiling add histograms, correlations and warnings about things like constant columns. My tool
does the core of that job, and it shows what those libraries are starting from.

## Known limitations

- A column of mixed values is labelled `text` and gets no stats, even if it's 99% numbers.
- `NA`, `n/a` and blanks count as missing, but `unknown` and `missing` don't, and they turn a number column into text.
- Only `YYYY-MM-DD` dates are detected.
- A file with more fields in a row than in its header, or a folder passed as the path, still ends in a traceback.
- The wrong separator isn't an error. The table just shows a single long column.
- `format_value`, `load_file` and the CLI have no automated tests. I checked those by hand.

## Tests written

| Test | What it checks |
|---|---|

| `test_constant_column_has_zero_std` | a std of 0.0 is kept as a real result |

To check that the tests do their job, I put bugs into a scratch copy of the profiler, one at a time:

| Bug added | Caught by |
|---|---|
| No "empty" check | `test_all_empty_column` |
| Date check keeps blanks | `test_date_column_with_missing_values` |
| Blanks counted as a unique value | `test_numeric_column_has_stats`, `test_all_empty_column` |
| Upside-down null % | `test_null_pct_with_known_missing_values`, `test_date_column_with_missing_values` |
| Std of 0 turned into `None` | `test_constant_column_has_zero_std` |

A test that can't fail isn't testing anything, so this is worth repeating on later builds.

## Open questions

If you are reading this, try these yourself. I have a rough mental model of the answers but have not built them yet.

- How would you label a column as "number with bad values" by measuring how many values convert with
  `pd.to_numeric(errors="coerce")`? What share should count as numeric?
- How would you detect the separator automatically, so `--sep` isn't needed? (`csv.Sniffer` is a place to start.)
- How would this change for a file too large to fit in memory, using `chunksize`? Which of the stats can be calculated
  one chunk at a time, and which can't?
- At what null % should a column be dropped rather than filled in, and does that depend on why the values are missing?
